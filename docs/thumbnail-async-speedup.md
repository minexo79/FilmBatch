# 縮圖載入加速方案（非同步管線化）

2026-10-25。狀態：**方案草稿，尚未實作**。與 `docs/perf-fix-plan.md` 互補：該文件處理 CPU／硬碟／記憶體爆量，本文件處理載入「速度」。

## 現況

縮圖載入本身已是非同步，但整條路徑是串行加節流：

| 位置 | 作用 |
|---|---|
| `FilmstripViewModel.PumpAsync` | 一次只處理一張：解碼 → 提交算圖 → 等送達 → 才取下一張 |
| `ImageCache._backgroundGate = new(1, 1)` | 背景解碼同一時間只有一個 |
| `ImageCache.PaceBackgroundAsync` | CPU 目標預設 70%，必要時在入場之間插入最多 2 秒閒置 |

縮圖已改走相機內嵌預覽（`d7a40bd`），單張成本很低，CPU 與硬碟大部分時間是閒的，等待時間主要耗在串行與節流。

挑選順序（必須保留）：目前焦點 → 可見範圍 → 明確編輯佇列 → 游標之後的資料夾順序。

## 改動項目

### A. 解碼與算圖重疊（建議先做）
解碼第 N+1 張的同時，讓第 N 張算圖與等送達。只多一層管線深度（上限 1 張預取），仍然有界。

- 改動：`PumpAsync` 在提交算圖後不立刻 await 交付，改為先預取下一張的 `GetThumbnailSourceAsync`，再等前一張送達。
- 風險：預取的那張可能在等待期間被「焦點／可見範圍」變動取代；取代時要取消預取，避免佔用閘門。

### B. 放寬背景閘門
`_backgroundGate` 由 1 改為 2（可試 3），以 `SemaphoreSlim` 限制，不無上限開 Task。

- 內嵌預覽是檔案 I/O 加小型 JPEG 解碼，並行效益明顯；完整 RAW 顯影路徑（已去背、無內嵌預覽）仍受 `_decodeGate`（核心數一半）約束。
- 風險：與前景放大搶資源。`d7a40bd`～`229ed42` 已限制並行度，B 不得讓前景 Full 解碼被餓死。

### C. 內嵌預覽路徑放寬節流
70% CPU 目標是為完整 RAW 顯影設計。內嵌預覽路徑可：
- 預設目標提高（例如 90），或
- 只對「實際走了完整顯影」的解碼計入節流。

風險最小、效益依量測決定；若 A、B 後已夠快則不做。

### 不在此範圍
記憶體預算與解碼閘門（`perf-fix-plan.md` 的項目 D）。建議 B 之前或同時處理，否則並行度提高後記憶體上限不明。

## 驗證
1. 基準：同一資料夾（`perf-fix-plan.md` 的 355 組 ARW+JPG，或 `verification-photo-corpus` 的 50 張副本）量「開始載入 → 全部縮圖送達」總時間、平均 CPU、讀檔速率、PrivateBytes。
2. 每個項目（A → B → C）單獨量測，再累計，保留各階段數據。
3. 回歸測試：`ThumbnailRetentionTests`、`FilmstripLoadingTests`、`BulkLoadingTests`、`OffThreadScalingTests`；新增「預取被取代時取消」與「焦點優先不被預取擋住」的測試。
4. 目視：捲動與點選期間縮圖仍優先載入可見區；載入中按 1:1 不卡頓。

## 預期與取捨
- 預期：A 約省掉每張的算圖等待；B 在 I/O 為主的路徑上接近倍數加速；實際數字待量測，不預先承諾。
- 取捨：CPU 與硬碟尖峰會比現在高，但持續時間縮短；總讀檔量不變。

## 選項（由使用者決定是否做）：載入中鎖定操作

### 構想
資料夾載入（掃描與縮圖）期間，不允許編輯操作，載入完成後才開放。目的：消除載入與操作的資源競爭，使上述並行度可以放心加大，也簡化優先序邏輯。

### 可行性：可行，成本低到中等
現有基礎：
- `MainWindowViewModel.IsLoadingPhotos`（`IsScanningFolder || Filmstrip.IsLoadingThumbnails`）已存在，並已驅動進度條與取消按鈕（`MainWindow.axaml:104-114`）。
- 已有 `CancelPhotoLoadingCommand`，載入可隨時中止。
- `CanExecute` 綁定機制（MVVM Toolkit）可直接掛在各命令上。

實作方式（擇一）：
1. **全域遮罩**：載入中在主視窗覆蓋半透明層，擋住所有輸入，僅保留取消按鈕。改動最小，約一個 axaml 區塊加一個綁定。
2. **逐項停用**：對套用預設、調整滑桿、評分、匯出、檔案切換等命令加 `CanExecute = !IsLoadingPhotos`。粒度細，但命令多、容易漏，維護成本高。

### 影響評估
| 面向 | 影響 |
|---|---|
| 好處 | 載入期間 CPU／記憶體可預測；優先序（焦點／可見範圍）可大幅簡化，甚至不需要；B 項可放心加大 |
| 代價 | 大資料夾（數百張）載入若需數十秒，使用者必須乾等，是明顯的體驗退步；目前可「載入中就開始挑圖」 |
| 與現行設計衝突 | `FilmstripViewModel` 的焦點優先、可見範圍優先、明確編輯佇列等機制，本來就是為了「載入中可操作」而設計，鎖定後這些變成冗餘；`SetVisibleRange` 與選取同步仍需保留 |
| 風險 | 載入失敗或卡住時使用者被鎖死，必須保證取消按鈕永遠可用、錯誤路徑會解除鎖定（`IsScanningFolder` 與 `IsLoadingThumbnails` 在取消、換資料夾、例外時都要歸零） |

### 折衷方案（建議優先考慮）
不完全鎖定，只鎖「會與載入搶資源的重操作」：
- 載入中允許：瀏覽縮圖、選取、評分、切換資料夾、取消載入。
- 載入中延後：放大到 1:1／Full 解碼、批次套用、匯出。

這樣保留「邊載入邊挑圖」的核心體驗，又避開最吃記憶體的 Full 解碼（`perf-fix-plan.md` 問題 2 的來源）。

### 建議
先做 A、B 並量測；若載入時間縮短到可接受（例如 355 張在 30 秒內），就不需要鎖定。鎖定只在「加速後仍不夠、且資源競爭實測是主因」時才考慮，且優先採折衷方案。

**是否採用鎖定：待使用者決定。**
